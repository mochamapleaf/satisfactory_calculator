# 戴森球计划(DSP)产线的 CPU 成本模型 —— 最终报告

日期 2026-11-21 · 适用游戏版本 0.10.34.x(2026-01 之后) · 配套系数文件 `model.json`

> **一句话结论:原版 DSP 每个逻辑帧(60 次/秒)都会把每台机器、每个分拣器、每条带子路径更新一遍,不管它在工作、等料还是堵满。**
> 所以 CPU 成本主要取决于**实体数量**,而不是利用率。想省 CPU,就要让同样产量用更少的实体:
> 机器用最高等级,增产剂用加速模式,不留闲置机器,用混带和直插减少分拣器与带子。
> 物流塔在笑笑和代码两边都显示不是大头。

## 0. 前置知识

| 概念 | 要点 |
|---|---|
| 逻辑帧 / UPS | 游戏逻辑每秒 60 次(1 tick = 1/60 s),3 秒的配方就是 180 tick。CPU 算不完时 UPS 掉到 60 以下,游戏时间整体变慢;生产统计按游戏时间记,"每分钟产量"数字不变,只是现实里要等更久。笑笑在第 18 期 11:31 说"默认逻辑帧每秒 30 帧",这与 SampleAndHoldSim 作者"保持 60 逻辑帧"的说法和社区共识不符,本报告按 60 处理。 |
| 渲染帧 vs 逻辑帧 | 渲染(GPU、绘制调用)只算看得见的东西,飞到太空里基本归零。逻辑(CPU)**所有星球都算**,这是本报告建模的对象。 |
| 实体组件 | 游戏按类型用 struct 数组存实体:`AssemblerComponent`(制造台、熔炉、化工厂、精炼厂、对撞机共用)、`InserterComponent`(分拣器)、`CargoPath`(一串连通的带子)、`StationComponent`(物流塔)等。每 tick 按类型整个数组遍历一遍。 |
| 内存带宽瓶颈 | Weaver 作者分析:原版 struct 很大,更新一个实体就要把整个 struct 读进缓存。后期瓶颈主要是读内存,不是计算,所以"一个实体每 tick 的成本"接近常数。这是 0.10.34 之前的代码;0.10.34 官方改进了数据访问,各类实体的相对权重可能变了。 |
| 多线程 | 2025 年官方重写了多线程,0.10.34.28281(2026-01-22)又做了缓存命中优化,帧耗时降 5–30%。多线程只是把工作摊到多个核上,**总工作量仍随实体数增长**。 |
| 性能面板 | 游戏内"性能测试"面板(笑笑第 18 期 13:13–14:11 有介绍)分为:主要逻辑(下分生产线、戴森球系统、战斗系统)、绘制调用、用户界面、物理、数据统计。**传送带和分拣器在面板里是同一个分类**(第 18 期 19:15)。 |
| 分拣器状态机 | 抓取(Picking)→ 去程(Sending)→ 放入(Inserting)→ 回程(Returning)。去程和回程只给计时器加一;抓取和放入要去查带子或机器。 |

## 1. 每类实体每 tick 做什么(代码证据)

### 1.0 证据从哪来、可信到什么程度

本机的 DSP 已卸载(`G:\SteamLibrary\steamapps\common\Dyson Sphere Program` 里没有 `DSPGAME_Data`),所以没有直接反编译原版代码。
代码证据来自 **Weaver** 模组(作者 Loom,https://github.com/TheAIBot/DSP_Weaver ,master 分支 2026-10-18 更新)。
Weaver 用自己的数据格式**重新实现**了各类实体的更新逻辑,并在此基础上改动了一些地方:带子里的货物存储方式、去掉锁、把电力计算并进各实体的循环、风机改成常数时间、加了休眠状态。所以它不是对原版的逐行照抄。

判断原版行为的依据有两类:
- **Weaver 读写原版存档字段的代码。** `CargoPath.updateLen`、`InserterComponent.idleTick` 和 `careNeeds` 都是原版字段,Weaver 加载时读进来、退出优化时写回去(`OptimizedCargoPath.cs` 48/57 行,`OptimizedInserter.cs` 104/368 行,`InserterGrade.Create` 43–51 行)。
- **休眠状态只存在于 Weaver 自己的数组里。** `AssemblerState` 和 `InserterState` 不写回原版 struct,readme 也把"Can go inactive…"列在它的优化清单里。

据此推断**原版没有休眠状态**。这个推断合理,但没有用原版反编译直接确认过。
DSPOptimizations(Selsion)当前源码里没有分拣器或机器方面的优化,只用来佐证戴森云和物流塔方面的结论。

### 1.1 制造类机器(制造台、熔炉、化工厂、精炼厂、对撞机)

- 代码:`Optimizations/Assemblers/OptimizedAssembler.cs` 的 `Update`(77–256 行)。
  https://github.com/TheAIBot/DSP_Weaver/blob/master/Optimizations/Assemblers/OptimizedAssembler.cs
- 三种状态各做什么:
  - **工作中**:`time += power × speed`,时间到了就给产物计数加上产量,并登记生产统计。
  - **产物堆满**:比较一次 `produced > 上限`(熔炼 100,组装为单次产量的 9 倍,其他 19 倍)就返回(109–187 行)。
  - **缺料**:逐个检查原料 `served < requireCount`,不够就把 `time` 清零后返回(215 行)。
- 三种状态都只是几次比较,成本是 O(1)。除此之外,每 tick 还要更新电力需求和 `needs`(告诉分拣器缺什么)。
- 官方开发日志:"each Assembler might only take a few hundred to a few thousand nanoseconds"。
  https://gpuopen.com/learn/dyson-sphere-program-new-multithreading/

**检验两个说法:**
- **Xinyu:"等分拣器的机器可能很便宜"——原版不成立。** 闲着的机器每 tick 照样更新,成本和工作中差不多。装了 Weaver 才会变便宜。
- **笑笑第 18 期 17:41–18:54:"没启动的机器比启动的耗多得多,可能十倍"——代码不支持"十倍"。** 她同一段里也承认两种状态都是 O(1)。
  她的结论"不要留闲置机器"是对的,但理由是:闲置机器照付成本、却不产出。

### 1.2 分拣器

代码:`Optimizations/Inserters/Types/OptimizedInserter.cs` 的 `Update`(128–368 行)。
https://github.com/TheAIBot/DSP_Weaver/blob/master/Optimizations/Inserters/Types/OptimizedInserter.cs

每 tick 先判断 `power < 0.1f`,断电就直接返回;然后按阶段分别处理。

**去程 / 回程:** 只给计时器加一,很便宜。

**抓取(手里空着,等货):**
- 当 `careNeeds` 为真时:
  - 目标不缺这种料,就设 `idleTick = 9`(152 行),之后 9 个 tick 什么都不做;凑叠中途的同类退避是 204 行的 `idleTick = 10`。183 行那处退避属于给发电机上燃料的分支,与此无关。
  - 目标缺料,则**每 tick 都去带子或机器上抓一次**。
  - `careNeeds` 字面意思是"关心目标需求",一般在往机器或研究站里送料时为真。它的具体赋值条件 **存疑**,原版代码里没看到。
- 不关心需求时(往带子上放、带子到带子):每 tick 都抓一次。
- 集装分拣器(grade 4,`stackInput > 1`)抓到第一件后会停在抓取阶段继续凑叠,直到凑满或等满 `Delay`(40000 时间单位)。
  每 tick 加的是 `InserterComponent.speed`。如果它是 10000(**存疑**),最多也就多等约 4 tick,额外成本有上限,而且很小。

**放入(手里有货,等着放):**
- 目标是机器且 `careNeeds` 为真:目标不缺料就设 `idleTick = 10`(309 行)。
- 目标是带子:每 tick 都尝试放入(287 行)。带子堵住时,它就每 tick 试一次。

原版的分拣器也不会因为邻居堵住而整段休眠。`InserterExecutor.cs` 172–193 行的那段检查是 Weaver 加的。

**官方实测:** 某存档里,分拣器任务一帧约 3.6 ms,整帧逻辑约 22 ms,占比约 1/6(比例是我算的)。

**检验 Xinyu 的假设:"等得越久的分拣器每 tick 都在轮询,所以更贵"——部分成立。**
- 成立的情况:等货源(带子空着)或等出口(带子堵住)的分拣器每 tick 都要查一次带子,这比去程、回程计时贵。
- 不成立的情况:等机器把料"吃完"的分拣器有 9–10 tick 的退避,是最便宜的状态。
- 不管处在哪个阶段,每个分拣器每 tick 都要被读一遍,所以**分拣器个数是一阶项**。

**笑笑第 18 期 19:21–20:57:"白爪老在空等,换成刚好够用的黄爪更省"。** 机制上说得通,但没有任何实测,影响 **存疑**。直接**少放分拣器**比给分拣器降级更有效。

### 1.3 传送带

代码:`Optimizations/Belts/OptimizedCargoPath.cs` 的 `Update`(1323 行起)。注意这是 Weaver 版本的实现:它把货物直接打包存进 `CargoPath.buffer`。原版的货物数据存在每颗星球一个的 `CargoContainer` 里,路径只存索引,所以分拣器查带子要多跳一次。
https://github.com/TheAIBot/DSP_Weaver/blob/master/Optimizations/Belts/OptimizedCargoPath.cs

- **更新单位是路径**(一串连通的带子),不是每一格带子。
- 一条路径每 tick 做三件事:
  1. 有出口时,把头部的货物交给下一条路径。没有出口且 `bufferLength <= 10` 时直接返回(1378 行)。
  2. 从尾部往前跳过已经挤紧的货物,`updateLen` 随之减小。整条堵满时 `updateLen == 0`,直接返回(1390 行)。
     跳过这一步本身也要扫描,但 `updateLen` 会跨 tick 保存,所以只有第一次扫描贵,之后很便宜。
  3. 剩下能动的部分,按不同带速的区段整体往前拷贝(1433 行 `Array.Copy`)。成本和能动部分的长度成正比,但拷贝的是连续内存,很快。
- 原版 `CargoPath` 也有 `buffer` 和 `updateLen` 字段,算法结构应该类似,但每条路径的具体成本会和 Weaver 版本不同。
- **结论:**
  - 带子成本主要看**路径条数**和**区段数**。分流器、流速监测器、物流塔接口都会把一条带子切成更多路径。
  - **长度**是次要项。笑笑第 18 期 29:14 也说"关系真的不大"。
  - **4 叠堆叠**不增加每格的成本,同样流量只需要约 1/4 的带子。

### 1.4 物流塔、无人机、运输船

代码:`Optimizations/Stations/StationExecutor.cs` 29–82 行。
https://github.com/TheAIBot/DSP_Weaver/blob/master/Optimizations/Stations/StationExecutor.cs

- 每 tick 对每座塔调用一次 `InternalTickLocal`,星际塔还会调用 `InternalTickRemote`,最后调用 `UpdateNeeds`。
- 但传进去的时间参数分别是 `time % 1163962800` 和 `time % 60`。这暗示**调度本身是按 timeGene 错开、每座塔每 60 tick 轮到一次**,而不是每 tick 都调度。
  这两个函数体属于原版代码,没有看到,**存疑**。
- 每 tick 真正逃不掉的工作,大概率是:
  - 飞行中的无人机和运输船的移动,成本和在飞的数量成正比;
  - 带子口的输入输出(`OptimizedStation.cs` 的 `UpdateOutputSlots` / `UpdateInputSlots`,带锁)。
- DSPOptimizations 以前给"进出物流塔的带子"加过多线程,v1.1.19 删掉了,因为官方已经自己做了。
  https://github.com/Selsion/DSPMods/blob/main/DSPOptimizations/README.md
- 笑笑第 18 期对物流的看法:
  - **总体量级**(22:35–26:58):物流"只占了一点点的运算量";星际物流优化后"比原来占的算力少特别多了","完全不注意也是没关系的";和工厂比是"九牛一毛"(转写稿误为"901毛")。
  - **相对排序**(23:18–28:09,代码中均未核实,**存疑**):星系内跨星球物流最贵,因为要算绕开天体的轨道;星际物流的主要开销是"什么时候该发货"的判断,所以要少放大塔;行星内物流很省。

## 2. 单实体成本估计(相对单位)

**单位:1.0 = 一台制造类机器(含它的耗电部分)在原版里每 tick 的成本。**

除了"各等级制造类机器成本相同"有代码依据外,**其他系数都是估计值,不是实测值**,括号里是我认为的合理范围。
MILP 求最优解只用到各项的**相对**权重,跟绝对时间无关。

| 实体 | 相对成本 | 依据 / 置信度 |
|---|---|---|
| 各等级制造台、熔炉、化工厂、精炼厂、对撞机 | **1.0**(所有等级相同) | 共用同一个组件,等级只改变 speed。中 |

**分拣器系数的推导。**
- 已知:分拣器占一帧逻辑时间的 s = 1/6(3.6 / 22 ms)。设机器占一帧的比例为 m,每台机器配 k 个分拣器,每个分拣器的成本为 x(以机器为 1)。
- 关系式:k·x / 1 = s / m,所以 x = s / (m·k)。
- 取 k = 3:
  - 若帧里只有机器和分拣器(m = 5/6),x ≈ 0.067;
  - 若机器只占一帧的 1/3–1/2(其余是带子、物流塔、电力、戴森球、战斗),x ≈ 0.11–0.17。
- 取 x = 0.12。这个比例来自旧版多线程的单个存档;多线程下各阶段的墙钟时间之比,只能近似代表 CPU 工作量之比。

### 2.1 换算成毫秒(只作数量级参考)

- **数据点 1,官方开发日志**(https://devtrackers.gg/dyson-sphere-program/p/81e22586-dev-log-the-new-multithreading-framework ):
  一个 10 万白糖/分钟的存档,"Logic frame time for the entire production line hits 80 ms"。
  日志没说是哪套框架,从章节位置看**推测是旧多线程**;CPU 型号未给出;这是多线程下的墙钟时间。
- **我的粗估(存疑):** 用最高等级设施加加速增产剂,10 万白糖约需 9.8 万台机器。
  按 1 + 3 × 0.12 ≈ 1.36 单位/台算,约 13–14 万单位;
  所以旧框架下约 **0.6 µs 墙钟/单位**。
- **换算到现版本:** 新框架快约 1.9 倍(22 → 11.7 ms),0.10.34 再快约 1.2 倍(TTenYX 的修正系数),
  得到约 **0.25 µs 墙钟/单位**,但只对那台未知配置的机器有效。
- **误差:** 机器数、CPU、线程数、版本都不确定,误差约 **10 倍**。
  这个数和官方"每台制造台几百到几千纳秒"不能直接比:后者是单核 CPU 时间,前者是多核墙钟时间。
- **数据点 2,GPUOpen 转载的日志:** 一个 680 万白糖/分钟的存档,在 Threadripper PRO 9985WX(64 核 128 线程)上,"non-critical frame time" 从约 100 ms 降到 43–46 ms。
  如果按上面每单位的成本外推,两个数据点相差几十倍。这说明"non-critical frame"的口径不同,或者那个存档的实体结构差别很大。我**无法调和**这两个数据点。
- **怎么用:** 绝对毫秒数只用来粗判"某台电脑能不能跑满 60 UPS"。某个产量在哪种 CPU 上能满帧,请直接查 TTenYX 的实测表(https://www.bilibili.com/opus/996341655755816960 ,表格是图片,没有逐条核对;作者说 0.10.34 之后要把旧数据乘约 1.2)。

## 3. 哪些布局选择真正有用

按效果从大到小排列:

1. **机器用最高等级。** Mk.III 1.5×、重组制造台 3×、位面熔炉 2×、负熵熔炉 3×、量子化工厂 2×、自演化研究站 3×。
   每台成本和等级无关,速度高几倍,机器连同它的分拣器就少几倍。这是最大的一项。
2. **增产剂用加速模式。** 机器数减半,代价是多出喷涂机和增产剂产线。
   增产模式能省原料和上游机器,但本级机器数不变。哪种更划算由 MILP 按配方自己权衡。
3. **不留闲置机器。** 闲置机器照样付成本,却不产出(§1.1)。
4. **混带。** 一个分拣器可以按需从混带上抓多种原料:原版有 `needs` 字段,Weaver 的带子代码里有对应的 `TryPickItem(index, length, filter, needs)`(953 行)。
   例如两进一出的配方,从 3 个爪变成 2 个爪(笑笑第 18 期 21:14–22:28),带子路径也随之减少。
   在本模型里每台约省 0.12–0.2 单位,属于中等收益。
5. **直插**(机器 → 分拣器 → 机器):省掉一条带子路径和一个分拣器。
6. **4 叠堆叠**:同样流量只要约 1/4 的带子和塔口。
7. **用分拣器分流代替四向分流器。** 笑笑第 19 期 23:06 说"白爪的分流比四向分流器更不吃性能"。
   按本模型:她那种布局用 2–4 个分拣器(0.24–0.5),对比一个分流器(0.3)加上它切出来的额外路径(0.1–0.3)。分拣器方案略好或持平,但两边的系数都没测过,结论 **存疑**。
8. **戴森云和黑雾。** 它们不在产线模型里,但在性能面板上经常是大头:帆打完就关掉弹射,黑雾养殖场按需关掉。
9. **物流塔数量、带子长度、分拣器等级:** 都是小项。

## 4. 给 MILP 用的线性成本模型

### 4.1 目标函数

规划器对每个配方模式 r 都有建筑数 n_r(整数)和工作量 x_r(见 `src/planner/lp.rs`)。新增一个"最小计算成本"目标:

```
compute = Σ_r n_r · ( c_bld[b_r] + c_sorter · k_r + c_spray · s_r )
        + Σ_i F_i · ( c_belt_item · h_i + c_station_item · t_i )
```

**每台机器的项**
- `c_bld[b]`:建筑 b 的单台成本,见 `model.json` 的 `buildings`。
- `k_r`:每台机器配几个分拣器。它是常数,建模时就能算出:
  `k_r = Σ_端口 ceil(单台端口流量 / 分拣器能力)`。
  - 混带模式下,所有输入合并成一个端口。
  - 分拣器能力取它本身的能力与带速上限(4 叠蓝带 120 件/秒)中较小的一个,所以通常 `k_r = 端口数`。分拣器本身的能力数据来自调查文档 §2.1.2,**存疑**。
  - 直插是布局层面的选择,不是配方的常数,不能对每台机器统一减 1。要么做成单独的模式,要么先不建模。
- `s_r`:每台机器分摊的喷涂机数。默认 0;要细化时,按"每条进料带 1 台喷涂机,一条带供 Nₘ 台机器"来分摊。

**按流量的项**
- `F_i`:物品 i 的总流量,等于 Σ_r(配方 r 产出 i 的量 × x_r),对 x 是线性的。
- `c_belt_item = (c_path + c_seg × L) / (带速 × 叠数)`。默认 L = 60、蓝带 1800/分钟、4 叠时,等于 (0.1 + 0.12) / 7200 ≈ **3e-5 每(件/分钟)**。
  它按满带折算,所以流量很小的物品会被低估:半空的带子和满带成本一样。要精确就得用整数带数 ceil(F_i / 7200),需要额外的整数变量。
- `h_i`:平均走几段带子,默认 1。
- `t_i`:经过几次物流塔。一次无人机运输是供应塔和需求塔**各算一次**,即 t = 2。
- `c_station_item = 塔成本 / 单塔通量`。
  - 行星内塔:3 / 28800 ≈ 1e-4,其中 28800 件/分钟是 4 条 4 叠蓝带。
  - 这个"4 条蓝带"是笑笑第 19 期 42:37 说的**小塔在最远距离(从星球对面运货)时的运力**,不是上限;离货源近时运力更高。
  - 星际塔的通量没有可靠数据,先用同一个数代替,**存疑**。

整个目标函数对 n 和 x 都是线性的。`k_r` 和 `s_r` 是常数,可以直接并入"按(配方, 模式)的建筑权重"。
现在的 `CostWeights.building_weights` 只按建筑 id 设权重;`lp.rs` 里的 `build_scaled`(181 行)已经有一个按配方单元 key 的建筑成本乘子 `scale`,可以照这个做法加一个按单元的附加成本。

### 4.2 不放进模型的东西

- **利用率:** 原版按台数 n 付费,不按工作量 x。MILP 本来就会把 n 取到刚好够用,这正好就是"不留闲置机器"。
- **分拣器等级、戴森云、黑雾:** 不建模。电网的成本已经摊进各实体的系数里。

### 4.3 示例(粗估,存疑)

1 万白糖/分钟,用 `data/dsp.json` 每种物品取第一个非替代配方递归计算,不含采矿、射线接收站、喷涂机和增产剂产线。

**方案 A:Mk.III 制造台 + 位面熔炉 + 量子化工厂,不用增产剂。**
- 共 34 722 台机器,其中研究站 9000 台。
- 成本:研究站 13 500 + 其他机器 25 722 + 分拣器(34 722 × 3 × 0.12)12 500 ≈ **5.2 万单位**。

**方案 B:换成重组制造台 + 负熵熔炉 + 自演化研究站,并用加速增产剂。**
- 共约 9 800 台,约为方案 A 的 1/3.5。
- 成本约 **1.4 万–1.6 万单位**,已加上约 1/10 机器数的喷涂机和约 1 700 台射线接收站。

两方案相差约 3–3.5 倍。增产剂产线本身还没算进去,它会把这个差距再缩小一点。

### 4.4 装了模组时

- **SampleAndHoldSim:** 远程星球的成本乘以 1/UpdatePeriod(默认 1/10),各实体的相对权重不变。
- **Weaver:** 整体约 1/3(作者自测,基准是旧版本)。闲置实体变得很便宜,但不是零。
  这时目标函数仍然可以用,但"闲置机器照付成本"这条不再成立。这部分没有实测。

## 5. 不确定性与下一步

1. **除"各等级制造类机器成本相同"外,所有系数都没有实测。** 校准需要 Xinyu 重新安装 DSP(本机已卸载),在沙盒里每次只摆一类实体来测。
   由于传送带和分拣器在面板里是同一个分类,测分拣器时要用箱子喂料、不接带子,测带子时不放分拣器。
   也可以用 `ilspycmd` 反编译 `Assembly-CSharp.dll`,直接确认 `careNeeds` 的赋值条件、`InternalTickLocal/Remote` 里的 timeGene 错峰,以及 0.10.34 的数据布局。
2. 原版行为是从 Weaver 的移植和它读写原版字段的代码间接推断的。0.10.34 改了数据访问方式,各类实体的相对权重可能已经变化。
3. 毫秒换算误差约 10 倍,而且两个官方数据点无法调和(§2.1)。
4. 物流塔调度频率、星系内物流的成本、分流器和分拣器分流谁更省、分拣器等级的影响:都只有机制推理或视频里的口头说法。
