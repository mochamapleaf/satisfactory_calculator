## 严重

### S1. The sorter coefficient 0.6 contradicts its own stated derivation (§2 table, model.json `sorter-*`, `per_machine_terms.sorter_cost`)
- The stated basis is "sorters ≈ 1/6 of the logic frame (3.6/22 ms), with 2–4 sorters per machine". Take machine = 1, sorter = x, k = 3 sorters per machine. Even if machines and sorters were the *whole* frame, 3x/(1+3x) = 1/6 gives **x ≈ 0.067**. With 2–4 sorters the range is 0.05–0.1. If machines and sorters are only part of the frame (belts, stations, power, Dyson and combat take the rest), x comes out *smaller* still.
- With x = 0.6, sorters are 1.8 of the 2.8 units per machine. They become the largest term in the objective (64 %), which would put them at roughly 2/3 of the frame, not 1/6.
- Consequences: §3 items 4, 5 and 7 (mixed belt, direct insertion, sorter-splitting) and §4.3 ("9.8 万单位") are all driven by the inflated sorter term. The 30 万-unit count in the ms calibration (§2.1) is inflated too; see S2.
- Fix: derive x from the ratio explicitly and show the algebra, giving ≈0.07–0.1 (range 0.05–0.3). Or, if 0.6 is kept for a reason not stated, give that reason and drop the "1/6" justification. Then recompute §2.1, §4.1 (c_sorter), §4.3 and model.json `sorter-*` / `sorter_cost`.

### S2. The ms-per-unit calibration (§2.1, §5.3, model.json `unit_time_estimate_us`) is built on mismatched data, and its error is understated
1. **Framework/version mismatch.** The only source for 80 ms is the devtrackers caption "A performance snapshot from a 100 K Matrix save. Logic frame time for the entire production line hits 80 ms". It sits in the pre-rewrite ("CPU is maxing out") section, the old framework. The model is labelled 0.10.34.x. In the same devlog the new framework cut logic from 22 to 11.7 ms (≈1.9×), and 0.10.34.28281 claims a further 5–30 % (TTenYX: 10–30 %, ×1.2). For the target version the same save is plausibly ≈35–40 ms, i.e. about 0.4–0.5× the old number.
2. **The unit count depends on S1.** With the sorter at ≈0.08, 9 万 machines × (1 + 3×0.08) ≈ 11 万 units, not 30 万. The old-framework figure then becomes ≈0.7 µs per unit. Applying (1) brings it to ≈0.3 µs again. The agreement with 0.3 is coincidental, and the report should show both corrections.
3. **Wall time vs CPU time.** 80 ms is multi-threaded wall time on an unknown CPU with an unknown thread count. Saying it "和官方'每台几百到几千纳秒'量级一致" (§2.1) is unfounded: the ns figure is per-assembler CPU time, and with N threads per-core time per unit is 0.3·N µs. Delete that sentence, or state that the two numbers measure different things.
4. **Error band.** The 9 万-machine figure is an unvalidated guess (proliferator use in that save is unknown, and mining is excluded). On top of that come the CPU, the thread count and the framework. §5.3's "误差可能有 2–3 倍" is too narrow. model.json's [0.1, 1.0] is the honest range, so the report should say ~10×.
5. **"万糖约 3 万单位 → 8–10 ms → 原版大致能跑满 60" (§2.1).** This only holds for top-tier buildings plus speed proliferator. §4.3's own Mk.III/no-proliferator case is 9.8 万 units → ≈29 ms → ≈34 UPS. State which build is meant.

### S3. "每座塔每 tick 都调度一次" is likely wrong; the station costs and recommendation 8 rest on it (§1.4, §2, §3.8, model.json stations)
- StationExecutor.cs:29–37 passes `num = time % 1163962800` to `InternalTickLocal` and `num2 = time % 60` as the timeGene argument to `InternalTickRemote` (lines 64 and 71). A `time % 60` argument strongly suggests the vanilla remote dispatch runs once per 60 ticks per station, keyed on the station's gene (staggered), not every tick. The local dispatch is likely gated the same way inside `InternalTickLocal`. The body of `InternalTickLocal` is vanilla code and was not inspected. → The claim "每 tick 调度" is **存疑, probably wrong**. Per-tick work is more likely drone/vessel movement (∝ craft in flight) plus slot I/O.
- The report also cherry-picks 笑笑's ep18 statements. It quotes her ranking of logistics costs but omits her magnitude statements:
  - 22:35 "物流运输系统只占了一点点的这个运算量";
  - 23:02 "现在的这个星际物流比原来占的算力是少特别多了 … 完全不注意也是没关系的";
  - 26:58 "星际物流占的这个CPU比起工厂来说是九牛一毛" (whisper output: "901毛").
- Fix:
  - downgrade the claim to "每 tick 调用 InternalTickLocal/Remote; 调度本身疑似按 timeGene 错峰(未核实)";
  - add her magnitude statements;
  - treat station costs as **unknown, possibly ≪10**;
  - in §3.8, say the station term matters little next to the machine count;
  - give a drones/vessels-in-flight term as the likely real driver.

## 中

### M1. §3.7 (sorter splitting is cheaper than a 4-way splitter) contradicts the model's own coefficients
- 笑笑's layout (ep19 23:01–23:16, 已核实) uses *several* white sorters in place of one splitter. In model.json that is k × 0.6–0.7 against splitter 0.8, so the model says the splitter is cheaper. The comparison only turns around if the extra belt paths a splitter creates are counted (0.4 per path, itself 存疑).
- Fix: show the comparison explicitly, splitter + extra paths vs k sorters, and state that the conclusion depends on unmeasured coefficients. If S1 is fixed (sorter ≈0.08), the sorter variant does win. Mention that.

### M2. §4.3 reduction factor is overstated
- I re-ran `count.py universe-matrix 10000` and got 34 722 machines (labs 9000, Mk.III 10 222, plane 11 875, quantum 1458, collider 833, refinery 1333). That matches the "3.5 万" figure.
- Applying the tier factors from data/dsp.json:
  - assembler 1.5→3: ×0.5;
  - smelter 2→3: ×0.667;
  - lab 1→3: ×0.333;
  - quantum, collider and refinery unchanged;
  - then speed proliferator: ×0.5.
- The result is ≈9.8k machines, i.e. **≈1/3.5**, not "1/4–1/6". The unit range "2 万–3 万" still roughly holds.
- Other problems in the example:
  - the example costs labs at 1.0 although the model says 1.5 (9000 labs, +4500 units);
  - ray receivers for critical photons (≈1.7k), miners, spray coaters and the proliferator line itself are all omitted;
  - "两者差 3–5 倍" should read ≈3–3.5×, before the cost of the extra proliferator line.

### M3. The DSPOptimizations "~15 %" claim is mistranslated and outdated (§1.5 戴森云 row, model.json `em-rail-ejector`)
- The README says "Ejected sails will impact UPS much less (~15%) when not visible". That most naturally means the impact drops *to* about 15 %, not *by* 15 %.
- The v1.1.19 changelog also says "disabled optimization for ejected sails".
- Fix: "看不见时帆对 UPS 的影响降到约 15%(该优化在 v1.1.19 已停用)", or drop the number.

### M4. The Weaver runtime model (§1.6, §4.4, model.json `runtime.weaver`) is oversimplified
- The 3.0–3.5× is a whole-game figure (已核实, readme). Most of it comes from work-stealing threading, SoA layout, statistics and power rework, not from inactivity. It also only applies to planets the player is not on: the readme says the planet you are on reverts to vanilla logic.
- The vanilla baseline was probably pre-0.10.34, and 0.10.34 already took some of the cache gains. The gain over current vanilla is likely smaller than 3×.
- "闲置实体接近免费" is too strong. Inactive sorters still call `UpdatePower` and `IsObjectPickFromActive`/`IsObjectInsertIntoActive` every tick (InserterExecutor.cs:172–193). They are cheap but not zero.
- A missing alternative: **SampleAndHoldSim** (已核实: default UpdatePeriod 10, "stable 60 logical frames", incompatible with Weaver). Under it, remote-planet cost is ≈1/UpdatePeriod and the cost per entity stays the same. That deserves a `runtime: "sahs"` entry, or at least a sentence.
- Blackbox's last stated compatibility is 0.10.28 (Thunderstore changelog). Note that it may not run on 0.10.34.

### M5. The evidence chain overstates the port (§1 证据来源说明) but can be strengthened from the same files
- The readme says neither "逐行移植" nor that every difference from vanilla is listed. Weaver changes the belt storage (CargoContainer removed, items packed into `CargoPath.buffer`; readme: "slightly decreases belt buildings update performance"). It also folds power into the entity loops, computes wind in constant time and drops locks.
  - So §1.3's `Array.Copy`/buffer details describe Weaver's belts. The vanilla `CargoPath` has a similar buffer, but the cost per path differs.
  - The report should drop the "逐行" and "readme 写明" wording.
- The core claims can be supported more strongly than the report does, from the Load/Save mappings:
  - `updateLen`, `idleTick` and `careNeeds` are **vanilla fields**: they are copied from and back to `CargoPath`/`InserterComponent` (OptimizedCargoPath.cs:48/57, OptimizedInserter.cs:104/368, InserterGrade.Create lines 43–51 using `inserter.careNeeds`).
  - The Inactive states (`AssemblerState`/`InserterState`) are Weaver-only arrays and are not saved back to vanilla structs.
  - The readme lists "Can go inactive…" under "List of optimizations".
  - Cite these. They justify "原版无休眠" better than the absence of a mention in the patch notes does.
  - The inference itself (Inactive = Weaver addition) is **reasonable and I accept it**. Still say "未经原版反编译直接确认".
- The headline "cost ∝ entity count" relies on the Weaver readme's memory-bandwidth analysis. Its basis is code from before 0.10.34, which explicitly "improved data access for assemblers and labs, as well as sorters". Add that the relative weights may have shifted.

### M6. The flow-based belt and station terms contradict the "按台数不按利用率" principle and have unit/definition gaps (§4.1, model.json `logistics`)
- `c_belt_item = (c_path + c_seg·L)/(1800·4)` charges per item of flow, i.e. it assumes fully loaded belts. A half-empty belt costs the same as a full one but is charged half. State this as a known underestimate for low-flow items, or add a per-item minimum such as ceil(F_i/7200) belts, which needs integer variables.
  - The arithmetic checks out: 0.7/7200 = 9.7e-5 ≈ 1.0e-4.
- `c_station_item`:
  - An item moved by drones passes through **two** stations, supply and demand. Define whether 20/28800 is charged per station or per hop, and if per hop, double it.
  - The "4 条蓝带" (已核实, ep19 42:37) is a *PLS drone worst-case-distance limit* ("你不管这个煤矿…从地球的对面运过来"). It is not a "全球运力上限", and it says nothing about ILS throughput, which model.json also divides by 28 800. Correct the wording and the ILS denominator.
  - Model.json attributes the claim to ep19, but the report text does not give an episode or timestamp. Add "ep19 42:37".

### M7. k_r details (§4.1, model.json `per_machine_terms`)
- "直插的链路可以减去 1" is not a constant of (recipe, mode). Whether a machine is direct-inserted is a layout decision, and subtracting 1 for every machine is wrong. Either make it a separate mode (a variable) or drop it.
- `sorter_capacity_items_per_s: 480` (120 cargo/s × 4) exceeds the belt maximum of 120 items/s, so it can never bind. The underlying 120 cargo/s comes from calculators-survey §2.1.2's wiki reading, which is itself 存疑. The conclusion k_r = port count holds either way. Say so, and cap the capacity at the belt rate.
- Implementation note: `build_scaled` in src/planner/lp.rs (around line 181) already takes a per-unit `scale` map keyed by `u.key`. The per-(recipe, mode) weight can use that hook instead of extending `building_weights`.

### M8. Calibration plan ignores how the performance panel groups categories (§5.1)
- 笑笑 ep18 19:15 says the panel shows "传送带和分拣器 … 其实是同一个东西", one combined category. The sandbox test must therefore isolate sorters from belts by build design (for example, sorters fed by chests), not by panel category.
- The panel tree she describes (13:13–14:11) also deserves a mention as the measurement tool:
  - 主要逻辑, containing 生产线, 戴森球系统 and 战斗系统;
  - 绘制调用;
  - 用户界面;
  - 物理;
  - 数据统计.

- L1. §1.2 "(152、183 行)": line 183 is the **FuelPowerGenerator** branch (fuelFull → idleTick=9), not careNeeds. The careNeeds lines are 152 (=9) and 204 (=10, mid-stack). Fix the citation.
- L2. §1.2 Delay 40000: Picking adds `InserterComponent.speed` per tick (vanilla constant, probably 10000; 存疑, not visible in the Weaver sources). If so, the stack-gathering wait is ≤4 ticks per cycle, so the "+0.1 集装额外项" is bounded and small. Say "≈4 tick". Grade 3 has a Delay of 110000, used only with the obsolete `inserterStackCountObsolete` setting.

- L4. §2.1 "旧多线程框架": the framework is not labelled in the devlog. It is inferred from the section placement, so write "推测为旧框架".
- L5. §6: the GPUOpen post (2026-02-12, guest post by Youthcat) is a repost of the 2025 devlog. Its large benchmark (6.8 M matrices/min, TR PRO 9985WX, non-critical frame 100 ms → 43–46 ms) is a second data point the report does not use. Mention it as a possible calibration cross-check: a much bigger factory on a known CPU.
- L6. §1.3: CargoPath.Update has a second early return, `bufferLength <= 10` with no output (line 1378). The jammed-path skip loop also scans the packed tail (`while buffer[num5]!=0`), so a jammed path is not O(1). It is cheap only because `updateLen` persists.
- L7. The §1.1 citation "约 77–256 行" is fine, but the blocked returns sit at 109–187 and 215; cite those.
