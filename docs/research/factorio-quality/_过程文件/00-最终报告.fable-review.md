## 严重

### S1. 齿轮 oracle 测试和"剪枝后子图"测试按原文会失败；回收配方进图后，剪枝基本失效（§3.3、§5 第 3、5 步）

原文：
- §5 第 3 步："测试：物品数 ≈ 固体数 × 5 + 流体数；剪枝后传奇齿轮子图只含齿轮、铁板和回收配方。"
- §5 第 5 步："齿轮：79.8786（容差 1e-6）"
- §3.3："scottmsul 的例子显示，放开所有配方后，最优解会去'借道'地下传送带，把输入降到 47.93。"

这三句互相矛盾。
- `lp.rs` 的 `relevant()` 是"谁的产物被需要就收进来"的上游闭包。回收配方的产物是原料，所以只要目标链里有铁板，**所有能回收出铁板的物品的回收配方**都会被收进来（传送带、地下带、机械臂、组装机……），接着它们的制造配方和其他原料也被收进来。传奇齿轮的"相关子图"实际接近整个游戏，不是"齿轮、铁板和回收配方"。
- 79.8786 这个数只在限定配方时成立。scottmsul README 的原命令带 `--allowed-recipes iron-gear-wheel iron-gear-wheel-recycling`（已打开核实）。不限定时 README 给的是 47.92572353617703。所以 Rust 测试如果不限定配方，得到的会是 47.93 附近（或我们数据下的另一个数），断言 79.8786 必然失败。
- 对用户也一样：默认放开全部回收配方，求解器会给出"先做地下带再回收"这类绕路方案，多数人不想要。

更正：
- 第 3 步增加一个设计项：**回收配方的允许范围**。建议默认只允许"目标物品及其直接原料链上的物品"的回收，另给"允许全部回收配方（找绕路）"的开关。对应 scottmsul 的 `--allowed-recipes`。
- 第 5 步的齿轮测试写明：只启用 `iron-gear-wheel` 和 `iron-gear-wheel-recycling`，只允许组装机 3。另加一条"全部配方"测试，不断言具体数值，只断言 ≤ 79.8786。
- 第 3 步的剪枝测试改成："限定回收范围后，子图只含齿轮、铁板、齿轮回收"；并补一条"全部回收配方时列数等于全量"的规模测试。
- §3.1 的规模估算要说明：放开回收后，**每次求解**都是全量规模，不是偶发的上界。

### S2. LDS shuffle 的"前提条件"写反了：铸造厂不需要装品质插件，研究只要 15 级而不是 25 级（§1.6、§7）

原文（§1.6）："前提条件：铸造厂的槽位要全装品质插件，同时产能还要在上限。铸造厂自带 +50 %，所以 +250 % 必须全部来自 LDS 产能研究；按每级 +10 % 算是 25 级（每级 +10 % 存疑）。产能不够时，就只能在'装产能插件（q_f=0）'和'环有损耗'之间权衡。"

独立重算（塑料守恒只要求 (1+p)×0.25 = 1，与品质从哪台机器来无关）：

| 方案 | 研究等级 | 每份普通塑料得到的传奇塑料 | 每份塑料的铸造次数 | 研究累计成本（1000×1.5^L 求和） |
|---|---|---|---|---|
| 铸造厂 4×传奇产能 3（q_f=0），回收机 4×传奇品质 3 | 15 级（50 %+100 %+150 %） | 1.000 | 14.9 | 约 131 万 |
| 铸造厂 4×传奇品质 3，回收机同上 | 25 级 | 1.000 | 7.7 | 约 7575 万 |

- 两种方案都是 1:1 无损。全品质方案只是循环次数少一半，但研究成本高约 58 倍。
- 研究不足 15 级时，逐级枚举整数配置的最优解（5、10、14 级）都是**铸造厂全产能、品质只靠回收机**，不存在原文说的那种权衡。例如 14 级时最优 (0,0,0,0)，塑料转换率 0.678。
- 笑笑自己的做法也是这样：笔记第 46 行"LDS 的 shuffle 在铸造厂，放最好产能插件，'整个产线产能放大最大的地方'"。报告 §4 引了他"生产机器装产能、回收机装品质"的分工，却在 §1.6 写了相反的前提。
- 这个错误来自第一轮 critic 的次要项 3，它把"铸造厂装品质插件时"的条件句写成了普遍条件，报告照搬成了"前提条件"。

更正：§1.6 改为"条件只有一个：铸造配方的总产能达到 +300 %。常规做法是铸造厂装 4 个传奇产能 3（自带 50 % + 插件 100 %），研究补 150 %，即 15 级；品质只靠回收机的 4 个品质插件。铸造厂也全装品质插件需要 25 级研究，循环次数减半（7.7 对 14.9 次/份塑料），但研究成本约高 58 倍。"并删掉"产能不够时……权衡"一句，换成上面的逐级结论。"每级 +10 %"已核实（见核实表），去掉"存疑"；§7 相应删除。

### I2. 采矿在我们的转换器里是"资源"而不是配方，第 3 步写的品质挖矿做不出来（§1.1、§3.1、§5 第 3 步）

原文（§5 第 3 步）："纯流体输入配方和采矿只生成 `r@0`。""资源和原料按裸 id 映射：`iron-ore@0` 要能被 `data.resource()`/`resource_weight` 识别"

`tools/convert_factoriolab.py` 第 10、72–88 行把带 `mining` 标记的配方转成 `resources`，`lp.rs` 里它们是 `raw_i` 变量：没有机器、没有插件槽、没有 mode。所以"采矿生成 k = 0…N 个品质插件的 mode"在现有结构下无处可放；同一段里"采矿是 r@0 配方"和"矿是 resource"两句也互相冲突。

更正：第 3 步明确写出改法，二选一。
- 把采矿改成真正的配方：输入一个虚拟物品"矿床"（它才是带权重的资源），产出 `ore@q`，机器是采矿机，带品质/产能 mode；采矿产能研究不设上限。
- 或者暂不做品质挖矿，在报告里写明这是已知缺口。此时 §0.1 的"LP 必须同时包含它们"要降级为"第二阶段"。

顺带：大型采矿机的"资源消耗 50 %"意味着"每消耗 1 单位矿床产出 2 矿"，按资源计价时要进系数，否则原料成本高估一倍。

### I3. 模型漏了催化剂（catalyst）：产能不乘催化剂部分（§1.1 末条、§2.1、§5 第 4 步）

原文（§1.1）："所以在模型里可以写成'产物 ×(1+p) 再按 q 拆分'。"

FactorioLab 数据有 `catalyst` 字段，`spa` 和 `2x1` 各 7 个配方：煤液化（两个）、Kovarex、`pentapod-egg`、`fish-breeding`、`quantum-processor`、`cryogenic-science-pack`。FactorioLab 自己的处理（`src/state/adjustment.ts` 第 342–350 行）是只对"产出 − 催化剂量"乘产能。

- 我们的转换器和 `rules.rs` 都没有 catalyst（grep 无结果），现在的 `out_mult` 对 Kovarex 这类配方已经算多了。这是现有 bug，不只是品质的问题。
- 与品质直接相关的是 `pentapod-egg`（1 卵 → 2 卵，催化剂 1，允许品质插件）。这正是笑笑 ep46 用来刷第一个传奇五足虫卵的配方。
- 催化剂产物是否参与品质掷骰，没有找到出处：**存疑**，实现前要在游戏里或 API 文档里确认。

更正：§2.1 的配方列写成"产出 = 催化剂量 + (原产出 − 催化剂量)×(1+p)"；第 2 步（研究产能和机器自带效果）加一条"转换器带出 `catalyst`，mode 的产物向量按上式计算"，测试用 Kovarex。

### I4. "整数机器"的建模与规模判断证据不足（§2.1、§3.1、§5 第 6 步）

原文：
- §3.1："≈ 1 万列，回收配方约 2 千列。LP 没有问题；整数机器 MILP 在 microlp 上是否在时限内收敛：**存疑，需要实测**。"
- §2.1："整数机器数则是 MILP，不需要任何新的求解器能力。"

三点：
1. 列数我用 `spa` 数据按报告的规则数了一遍：非科技配方 659 个，全部生产机器 × 输入档 × 品质/产能 mode 共 **8889 列**，回收 2790 列（回收机按 2 种 mode 算）。量级与报告一致。但 `lp.rs` 每列有 x 和 n **两个变量加一条约束**，开功率权重时还多一个变量和若干条约束；机器品质、插件塔再各乘一维。实际是 2.3 万变量起。"LP 没有问题"没有任何实测支撑，HiGHS 能解不代表 microlp 在 WASM 里能解。另外 `build_scaled` 建平衡行是"物品 × 列"的双重循环加字符串比较（约 2800 物品 × 1.2 万列），`relevant()` 每轮扫全部列，这两处在这个规模下本身就可能要秒级。
2. 整数机器的语义与实际玩法不符。`lp.rs` 给每一列一个整数 n。品质环里优秀、稀有、史诗、传奇四档的工作量分别只有普通档的 14 %、4.6 %、1.4 %、0.3 %，逐列取整会给每档至少 1 台。笑笑的做法是"7 台普通 + 1 台自动切配方做所有高品"共 8 台。要表达这一点，需要"共享机器"约束：同一机器类型、同一插件配置的若干列共用一个整数 n，Σ(x/speed) ≤ n。这是模型结构的改动，不是"不需要任何新的求解器能力"之外的小事，应写进第 6 步。
3. 插件预算、插件计价（`held`）在混装时每列要带两种 `module@q`，现有 `held` 支持；这一点没问题。

更正：在第 1 步之前加"第 0 步：规模试验"。用合成的 1.2 万列品质 LP（可直接从 `2x1` 数据生成）在 microlp/WASM 里计时；结果决定默认是否必须限定回收范围（S1）。第 6 步加"共享机器（切配方）"约束，并说明不加时整数解会高估高品档机器数。

### I5. "7:1 吻合"只在"4 槽全品质"这一种配置下成立，而这不是模型自己的最优配置（§0.4、§2.5、§4）

原文（§4）："模型在全传奇品质 3 的假设下给 7.09:1，与之吻合。但这个比例对插件等级敏感（§2.5）"

重算（回收机 24.8 %，传奇插件）：

| 组装机 3 每档配置 | 普通档 : 优秀–史诗档 合成次数 |
|---|---|
| 0 品质 4 产能 | 4.12 |
| 2 品质 2 产能（模型的最省原料解） | **5.03** |
| 4 品质 0 产能 | 7.09 |
| 电磁工厂 5 品质（自带 +50 %） | 3.68 |

- 比例对"品质/产能配比"和"机器自带产能"的敏感度比对插件等级更大，报告只写了后者。
- 7.09 对应的是**不允许产能插件的配方**（插件本身、机器、装备等成品），这时 4 槽全品质就是最优，笑笑的原话也是"对于放品质插件的组装机配方"（笔记第 78 行）。对允许产能的中间产品，模型最优是 2 品质 2 产能，比例是 5.03，全品质配置多耗 45 % 原料（116.05 对 79.88）。

更正：§0.4 和 §4 写成"对不能装产能插件的配方（4 槽全品质），模型给 7.09:1，与他的 7:1 一致；允许产能的配方在最省原料配置下是 5.0:1；电磁工厂全品质是 3.7:1"。§2.5 加上表。

另有一条报告没用上的佐证，可以补进 §4：ep46"这个配方平均刷 4 次就能生一个传奇"（史诗 → 传奇，机器挂满品质插件）。史诗档升传奇的概率就是 q，4×6.2 % = 24.8 %，期望 4.03 次，吻合。

### I6. 2.1 的 LDS 状态不必再"存疑"；同时 2.1 的 API 让几条模型假设变成了数据属性（§1.1、§1.6、§7）

- FactorioLab `2x1`（2.1.25）里 `casting-low-density-structure` 没有 `disallowedEffects`，而三个再处理配方有 `quality`。

更正：§1.6 改为"2.1.25 仍有效（FFF-442 开发者原话 + 2.1.25 数据）"，从 §7 删除。

另外，2.1 版本史（Version_history/2.1.0 后半页，子版本号页面摘录里看不到）和 lua-api 2.1.25 新增了几项，报告的假设因此要改成"读数据"：
