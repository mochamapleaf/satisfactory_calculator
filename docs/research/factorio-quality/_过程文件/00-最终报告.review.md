# Critic review: 00-最终报告.md (factorio-quality)

Reviewer: adversarial critic subagent, 2026-11-21. Script re-run: `python -I quality_lp.py`.
Checks used extra reconstruction code (critic scratchpad `chk.py`…`chk4.py`); the relevant logic is described inline so it can be ported into `quality_lp.py`.

Overall: the core model (item@q columns, transition matrix with overflow into legendary, productivity before split, recycler 25 %·Q(q_r), legendary not recycled, lower-triangular closed form) is **correct**, and every headline number I could recompute matches. The problems are: one missing major mechanic (quality modules on fluid-only recipes and mining drills), a supporting script that doesn't actually produce half of what §0/§2.4 say it reproduces, an implementation plan that understates the code change and contradicts the plan already in the survey, and some overclaiming around 笑笑's numbers.

## CRITICAL

None. No fabricated sources, no wrong core math.

## MAJOR

### M1. Quality routes are missing: fluid-only recipes and mining drills can take quality modules (§1.1, §3, §5)
- §1.1 files "纯流体输入的配方：产物默认是普通品" under "没有品质或不吃品质插件". The wiki Quality page says they have no quality *variants*, but "Any items they produce are Normal unless quality modules affect them". So quality modules **do** work on them. Examples: foundry casting plates from molten metal, holmium/electrolyte chains. These are standard ways to get quality plates directly from normal ore.
- Mining drills take quality modules and produce quality ore in vanilla Space Age. Sources: forum thread https://forums.factorio.com/viewtopic.php?p=651771 (dev reply: intended); QualityPrototype `chain_probability` text says "crafting/mining operation". Mining productivity is uncapped (wiki Productivity: miners are not subject to the 300 % cap). FactorioLab `spa` mining recipes (`iron-ore-mining` etc.) have no `disallowedEffects`, so the data already allows it. The report lists the big mining drill in §1.3 but never says it can roll quality.
- Why it matters: both are competing routes the LP has to see. "Legendary ore → whole chain at legendary" competes with recycler upcycling on every objective. If the planner omits them, it will report a non-optimal "optimum".
- Fix:
  - §1.1: move fluid-only recipes out of the "不吃品质插件" list. State that they accept quality modules, have only a tier-0 input column, and split their solid outputs by Q(q)[0,·].
  - Add a bullet on quality mining: big mining drill, 4 slots, quality ore, uncapped mining productivity.
  - §3.1/§5 step 3: mining and fluid-only recipes get k = 0…N quality-module modes like any other recipe, with a single input tier.
  - §7: add the exact quality-mining odds to the 存疑 list (no official page found).

### M2. `quality_lp.py` does not produce several numbers the report says it reproduces (§0.2–0.3, §2.4)
- Script section B prints `EM plant 5xQ3L every tier: 0.04259 legendary per normal input (wiki 0.013)`. The report says 0.01299. The two use different metrics, and the script's label is misleading.
- The script's "LP optimum" lines are per normal *ingredient*: `EM plant: 7.556346 %`, `AM3 1.251900 %`, `foundry 4.124319 %`. The report's table (2.722332 / 0.583017 / 1.608046 / 0.341205 % integer; 1.624291 / 0.586222 / 0.344068 % fractional) appears nowhere in the script output. A reader who runs the script sees numbers that seem to contradict the report.
- I independently confirmed the report's values:
  - Wiki metric = legendary per 1 normal **product** entering the recycler, i.e. start vector 0.25·Q(q_r)[0,·]. Wiki: L = A·R + C, L¹⁰⁰ bottom-left.
  - EM all-quality with legendary tier p = 0.5: L¹⁰⁰[4,0] = **0.0129902**.
  - Integer enumeration and the LP (mixing allowed) both give chem 0.341205, AM3 0.583017, foundry 1.608046 at (1,1,1,2), EM 2.722332 at (1,1,1,1), cryo 4.835199 at (0,0,0,0).
  - Continuous optimisation over fractional k gives chem 0.344069, AM3 0.586214, foundry 1.624291, EM 2.722439. The report's 0.586222 / 0.344068 differ in the 5th–6th digit: an optimiser tolerance; quote at most 4 significant figures.
- Fix:
  - Add a section "F. wiki yield table" to `quality_lp.py`: the wiki-metric start vector, the integer LP, the fractional optimiser and the L¹⁰⁰ check.
  - Relabel B (e.g. "legendary per normal ingredient; wiki's 0.013 uses per-product metric, see F").
  - Make every number in §2.4 and §0 appear in the script output.

### M3. Implementation plan understates the code change and diverges from the existing plan (§5 steps 2–4)
- Inputs are not handled. §5.3 adds only `outputs: Option<Vec<…>>` to `Mode`, but a tier-i column must also consume `ingredient@i`. `lp.rs` builds the balance rows from `r.inputs` plus `extra_inputs` (lp.rs ~L280–290), so inputs need an override too. Alternatively, expand recipes as well: the survey's existing plan (calculators-survey.md §2.2.3 and implementation list: "expand … each recipe into `recipe@input_quality`"; "item@q / recipe@q expansion in the data layer; no solver change"). The report's §5.2 expands only items and doesn't explain why it departs from the survey plan.
- "lp.rs 只读这个向量，求解器其余部分不改" is not true. `r.outputs`/`r.inputs` are also read by:
  - `relevant()` (L62–84, graph pruning);
  - `items_of()`;
  - `finish()` (L465–470, the RateLines shown in the result table);
  - the Sankey / item-flow tab.

  Resources are matched by bare item id (`data.resource(it)`, `resource_weight`), so `iron-ore@0` won't be priced as a raw resource unless the expansion maps it.
- Supplies cost 0 in lp.rs (`sup … p.add_var(0.0, …)`). So the proposed test "gear LP = 79.8786" with iron plate as a *supply* has no input cost to minimise. The test must make `iron-plate@0` a weighted resource, or add a supply cost.
- Research productivity is missing. The survey orders "modules + beacons + **research productivity** … then quality expansion". The report's plan has no research-productivity step, yet:
  - the LDS shuffle (§1.6) depends on research reaching the 300 % cap;
  - EM/foundry optima change with research levels.

  Current `tiered_modes` also ignores machine base productivity (no `baseEffect` in the current data).
- PROGRESS.md has no "步骤 10 品质按 item@q 展开"; grep finds no quality step there. The plan lives in `docs/research/calculators-survey.md` (§2.2.3, implementation step 5). Fix the citation.
- Fix:
  - §5.2–5.3: choose recipe@q expansion in the data layer, as in the survey, or give Mode both input and output overrides, and list the touched functions (`relevant`, `items_of`, `finish`, resource lookup, Sankey, item values).
  - Add a step "research productivity per recipe (+10 %/level, cap 300 % including base)" before quality.
  - Fix the gear test so plates carry cost.

### M4. "27:1 应是两千七比一，转写漏了千" is overclaimed (§0.4, §4, §7)
- Per the notes, 笑笑 says "27比1" in ep39 (04:53), ep42 (00:30), ep43 (06:23), ep46 (38:58) and ep52. It is unlikely that ASR dropped "千" the same way five times across episodes.
- What is supported: his own "27K 只回收出 10 个" (≈2700:1) and the model's 2726.9:1 agree. "27比1" is best read as his verbal shorthand or a slip.
- Fix: "他多集一贯说'27比1'，但他自己给的'27K→10个'对应约 2700:1，与模型 2726.9:1 一致；'27比1'应是口头简称/口误（存疑），不是转写错误". Drop the claim that the transcript omitted 千. Also note the 2.1 value: q_r = 0.25 gives **2682:1**.

### M5. The 7:1 comparison is weaker than presented; the 7.70 / 9.41 ratios rest on an unstated assumption (§0.4, §2.5, §4)
- 7.09 needs all 4 slots legendary Q3 *and* a 24.8 % recycler.
- The 7.70 (5 %) and 9.41 (2.5 %) values keep the recycler at 4×legendary Q3 while downgrading only the assembler modules. If the recycler uses the same modules, the ratios are **8.49** and **15.90** (recomputed).
- The ratio also depends on whether legendary-tier crafts count toward the "one high-quality machine": 7.09 without them, 6.99 with them.
- His tier of quality modules in ep41 is not stated in the notes ("插件全放最好的").
- Fix: state the assumption (recycler fixed at 24.8 %), add the same-module numbers 8.49 / 15.9, and soften "对得上" to "在全传奇品质3假设下与 7:1 吻合；比例对插件等级敏感".

## MINOR

1. **§0.3 / §6 wording "连续松弛".** The wiki explains its fractional rows as several machines with different ratios at one tier. The report should quote that and then refute it. A mix of machines is a convex combination of columns, which the LP already includes; the LP with mixing gives exactly 0.583017 for AM3. The wiki's 1.67 Q is therefore not realisable: it plugs fractional k into the nonlinear (1+p(k))·Q(kq) product. "连续松弛的上界" is loose wording. Use "把小数插件数代入非线性产出公式得到的值，高于任何真实机器组合". The conclusion itself is **correct**: LP max 0.583017 < 0.586191.
2. **§1.6 mod-page claim.** The no-quality-cheesing page for 2.1 says only "Forbids using quality with the 'Casting low density structure' recipe". It does **not** say the base game closed the space casino; that is an inference. Reword. Supporting evidence to add: the 2.1.0 version history (both halves searched) has no LDS/casting/quality-cheese line, and the 2.1.7 line disallows quality only on asteroid reprocessing.
3. **§1.6 LDS 1:1 claim.** The claim is correct in expectation:
   - LDS recycles to the standard recipe; FactorioLab `low-density-structure-recycling` gives steel 0.5, copper 5, plastic 1.25, time 0.9375 = 15/16.
   - Recycling keeps quality (wiki Recycler: "same quality as the item being recycled").
   - (1+3)·0.25 = 1.

   It holds only if productivity is at the cap **at every tier while the foundry holds quality modules**. That means research alone must supply +250 % (base 50 %), i.e. 25 LDS-productivity levels. Otherwise the foundry holds prod modules and q_f = 0. State this explicitly. Also mention the losses that are outside the LP: per-machine productivity-bar resets when inputs change, and the stochastic 1.25 return.
4. **§1.4 LDS recycling source.** The Recycler wiki page doesn't cover LDS, and it says items with multiple *viable* recycling recipes become non-recyclable. Cite the FactorioLab `spa` recipe above for the LDS recycling outputs.
5. **§5 step 1 "回收配方字段存疑" can be resolved now.** FactorioLab `spa` (2.0.77) has 279 recipes flagged `recycling`, with `disallowedEffects:["productivity"]`. Times already include /16. Self-recycles return 0.25 of the item itself (`uranium-238-recycling`, `biter-egg-recycling`). Other facts from the data:
   - There is no per-recipe `allow_quality`/`maximum_productivity` field. Restrictions come as `disallowedEffects` on recipes and machines.
   - Machine base productivity comes as `baseEffect`.
   - Quality tiers come as top-level `qualities`, with legendary level 5.
   - `beacon.profile` exists.
   - The 2.0.77 data still allows quality on `*-asteroid-reprocessing`; the 2.1 change must be patched in.
6. **§2.5 quality-calc "也用 0.124 / 0.8".** `0.8` appears in its `matrix.lua` docs ("0.8 for a space casino"); `0.124` was not found in its source (存疑). MIT is confirmed via the mod-portal API.
7. **Missing alternatives / prior art.** Factory Solver (mod, MIT, handles quality recycling loops) is already in calculators-survey.md and should be cited in §3 as prior art. FactorioLab itself also models quality. Mention both in one line.
8. **Machine-count claim (§2.3).** Correct: input-optimal 19.99 machines, min-machines 15.53 machines / 96.31 plates/s. Speed assumptions are right: quality scales only positive effects, prod3 −15 % and Q3 −5 % are unscaled, recycler 1.25×0.8. The script prints only the min-machine number; print the 19.99 too.
9. **§2.5 asteroid 0.0210.** State the inverse (≈47.7:1) for comparability with the other ratios.
10. **§1.2 table.** Q3 legendary 6.2 % is the 2.0 value; the Module page now shows 6.25 %. The table header says "2.0 数值", which is fine.
