### S1 §3.4 第 2 条、§6 第 0 步 (b):`fx_sci6_mod_b4_pow` "无方案"的原因诊断错了

- **报告原文**:LP 加 4 个重加权 LP 用了 2.0–3.8 s,"最后的全量 MILP 只剩 50 ms、0 节点",受限 MILP 的方案因此被丢掉。修法 (b) 是"LP 耗时计入预算"。
- **基线数据**(`base4s.jsonl`):
  - 各阶段时刻:`t_support` 2024.6 ms,`t_sub` 3026.3 ms,`t_end` 4003.4 ms。全量 MILP 实际有约 **977 ms**,解了 **103 个节点**。
  - 受限 MILP 找到了方案:`sub_obj` 387.531865,与 `ceil_obj` 相同。
  - 全量 MILP 的 `traj` 每一行的 incumbent 都是 `NaN`(3439/3692/3944 ms),界一直停在根 LP 的 322.44。也就是说,hint 从来没有被采纳。
- **审稿人复跑**:
  - 4 s:全量 MILP 254 个节点,仍然无 incumbent。
  - 12 s:全量 MILP 约 7.5 s、1825 个节点,`sub_obj` 仍是 387.53,但全量 MILP 依然没有 incumbent。
- **结论**:原因是全量模型拒绝了 warm-start hint(根因未查明),不是时间不够。
- **报告数字的来源**:
  - "0 节点"只出现在 `dump.jsonl` 那一次运行里(那次跳过了受限 MILP,`t_end` 1919.8)。
  - "3.8 s"在任何数据文件里都找不到;各次运行的 LP 加重加权 LP 是 1.47–2.02 s。
- **旁证**:linpow 变体去掉了 p 变量,同一流程里 hint 就被接受了(`var_linpow`、`v2_dom_lin` 都得到 387.53)。所以 §1.5A、§4.2 说的"线性功耗消除一类无方案失败",其实绕开了 hint 被拒的问题,并没有修好它。
- **改正**:
  - §3.4 第 2 条改为:
    > 大模型(2439 列 × 14 446 行,Power 目标):受限 MILP 找到 387.53,但全量 MILP 拒绝了由它生成的 hint(以及向上取整的 hint)。给 977 ms 解了 103 个节点没有 incumbent;12 s 时 1825 个节点也没有。原因未查明,疑与 p 变量在分段行上的 hint 值有关:去掉 p(线性功耗)后 hint 被接受。
  - §6 第 0 步:保留 (a)(用受限 MILP 的解或取整方案生成 Plan)。在 (b) 旁注明"与本例无关,只是防止 LP 阶段吃掉预算"。新增 (d):打开 microlp 的 debug 日志,它会打出 `warm-start hint rejected …`,据此查清 hint 被拒的原因。还要检查其他带 p 变量的模型有没有静默拒 hint:在本数据里只发现这一例和 Somersloop 三例(后者是预期内的)。

### M7 §4.1 第 3 条、§3.2 第 3 条、§6"不建议"第 2 行:"关 warm start 换 dual fixing"这个说法不成立

### M8 §5.1 局部搜索的前提写错了

- **报告原文**:"一个支持集的整栋方案就是它的 LP 向上取整。"
- 这个说法不对。向上取整只是该支持集上的**一个**可行整栋方案,是上界。该支持集上的整数最优可以更好:把工作量在几列之间挪动,可以填满取整浪费的那部分。受限 MILP 常常比取整好,就是这个原因(`sub_obj` < `ceil_obj`,例如 hmf7 42.71 对 46.78)。
- **改为**:"用支持集 LP 的向上取整作为该支持集的(上界)评价,一步只要一次 LP。"

### M10 漏掉的方案(b 节)

- **按"栋"设绝对 gap**:建筑数目标下,用户关心的是"离最优不到 1 栋"。可以设一个绝对 gap,例如 <0.5 栋,或用 lattice 判断上下界之间已经没有更好的整数值。这比把相对 gap 从 1e-4 放宽到 1e-3 更有意义,却完全没有讨论。
- **在 `lp.rs` 里自己加根节点割**:报告说 microlp 没有割平面,但没有考虑在建模阶段加模型专用的有效不等式。例如对每个物品:Σ_r c_r·n_r ≥ 需求 是整数背包,可以加 MIR 或 Chvátal–Gomory 割;再如对单产物链加 n ≥ ⌈下界⌉。这正好针对 §3.5 说的"取整看不见",工作量介于"化简"和"换 HiGHS"之间。
- **多 Worker 并行**:浏览器有多核,可以让 microlp 和 HiGHS 同时跑并取较好者,这样也能把 M5 的 6 s 压回 4 s。没有讨论。
- **其他 WASM MILP**:例如 glpk.js 没有提;即使不打算用,也应一句话说明为什么不选。

**理论**:
- **线性功耗替换是精确的**:c_max = 1 时有 5 条分段,a = 1、b = 0,所以 p ≥ P·x/speed + beacon·n。p 只出现在目标里(只在 w.power > 0 时建),把系数移到 x 和 n 上与原模型等价。
- **删支配列在 `lp.rs` 的模型下是可靠的**:
  - 把列 k 的 (x, n, s) 全部并到 j:容量 c_j·(n_j + n_k) ≥ x_j + x_k;
  - shard 行是线性的,可以相加;
  - 功耗取各分段的最大值,即插值函数 g 的透视函数,它是次可加的;而且 g ≥ 0 且单调,所以 P_j ≤ P_k、speed_j ≥ speed_k 时功耗不增;
  - 持有物 j ⊆ k,预算行不会变紧;
  - wb 含 building_weights、分拣器、插件和 beacon,可以覆盖 Custom 目标。
  - 仅有的两个注意点:每列上限 MAX_BUILDINGS = 1e6(实际不会碰到),以及平局时方案会变(M12)。
- **"向上取整总可行"**:除 Somersloop / shard 预算外成立。
