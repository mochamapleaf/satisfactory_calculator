## 一、严重

### S1. 原油被当成“不设上限的可再生资源”，但它其实是会采到下限的有限储量；“L=6 就能无限研究”因此不成立

**原文（§4.3 三层答案 1）：**
> 不用固态珍奇也能无限研究。……阈值测试（每种有限矿的上限设为 B_r/S(L)，原油、水、硫酸不设上限）在 L=6 即可行，与此一致。

**原文（§5.3 约束 4）：**
> 星区初始合计只有 404.8/s，到 L80 也只有约 ×9

**问题：**
- 油泉的产率正比于它的储量 `amount`（代码注释 “times 4e-5 for oil”），每采出原油就按 0.94^L 的概率扣储量，直到下限（0.1/s，对应 amount=2500）。它和固体矿是同一种“储量 × 0.94^L”的结构，所以 §4 的判据 a·S(L) ≤ B 同样适用于原油。
- 旁证：0.1 倍档每采 1 个原油扣 1 点储量时，时间常数 = 1/4e-5 s = 25000 s，半衰期 = 25000·ln2/3600 = 4.81 h，正好是 BWIKI 的“5 小时”。（这一步是我由半衰期反推的，没有读游戏源码，见“未能核实”。）
- 本种子油泉储量合计 = 404.8 / 4e-5 ≈ **1012 万点**（还要减去每个油泉 2500 的下限）。代入判据：

| 情形 | 每白糖原油 | a·S(6) | 满足 a·S(L) ≤ 1012 万的最小 L | 到该级的累计白糖 |
|---|---|---|---|---|
| A（用珍奇） | 15.5 | 1264 万 | 19 | 36 万 |
| F（增产） | 18.3 | 1492 万 | 25 | 76 万 |
| E（避开珍奇） | 32.5 | 2650 万 | 40 | 238 万 |

- 所以三种情形在 L=6 都**不**可行。情形 E（报告推荐的“不用珍奇”方案）反而最差：它把原油用量翻了一倍多。
- “初始合计 404.8/s，L80 时 ×9”也不是可持续速率。0.1 倍档 L0 时全星区油泉采到下限一共只能出约 1000 万个原油：按 15.5/白糖，只够约 65 万白糖。两万糖/分的厂半小时就把油泉采到底。

**修正：**
1. 把原油列为有限储量 B_oil = Σ(amount_i − 2500)，和固体矿一起进入 a_r·S(L)/(1−φ) ≤ B_r。
2. 采到下限后才是速率约束：N_seep × 0.1·(1+0.1L)/s。N_seep 目前拿不到（见 I5）。
3. 重写三层答案第 1 条：能否“不用珍奇无限研究”取决于原油，本种子按情形 E 要先到 L40。
4. §0.3、§5.3 里“原油很可能是硬约束”改成有数字的结论，并把上表放进 §4.3。
5. `rawpercube_main.rs` 的阈值循环给 crude-oil 加上限后重跑。

### S2. 情形 E 的“稀缺度权重 = 1/储量”得出了方向相反的建议

**原文（§4.3）：**
> 情形 E：按该种子储量的稀缺度加权（权重 = 1/星区储量）。LP 自动避开全部固态珍奇。

**问题：**
- 报告自己的判据说：只要 a_r·S(L) ≤ B_r，珍奇 r 永远用不完，它的真实稀缺度（影子价格）是 0。权重 1/储量却不管用量离上限多远，一律对珍奇罚重分。
- 同一次运行里原油的权重被设成 0.001（`rawpercube_main.rs` 第 35 行），几乎免费。结果 LP 用 32.5 个原油换掉了本来在配额内的珍奇。结合 S1，原油才是本种子最紧的资源。
- “LP 自动避开全部固态珍奇”是权重设定造成的，不是种子的性质。报告没有做任何权重敏感性分析，却把它写成结论，并在“三层答案”里据此手算。
- 正确的写法报告自己在 §4.3 末尾和 §5.3 已经给了：珍奇按约束（配额）进入，不按权重。目标应是最少建筑数或最少原油，约束是各资源 a_r·S(L) ≤ B_r。这样的 LP 会把珍奇用到配额上限。

**修正：** 删掉情形 E/F 作为“答案”的地位，改成“带储量约束（含原油）的最少建筑数 LP”，重跑后再写三层答案。E/F 可以留作对照，但要注明权重是人为设的。

## 二、重要

### I1. 一次性建筑材料 K_r 没有乘 0.94^L，量纲混了

**原文（§4.1）：**
> 判据变为 U_r + K_r + a_r·S(L)/(1−φ) ≤ B_r

§5.2 终端约束和 §5.3 约束 2（“B_k − K_k”）同样。

**问题：** B_r 是矿脉储量，K_r 是物品个数。在矿物利用 L 级时采 K_r 个矿只扣 K_r·0.94^L 点储量。45000 个磁石：L20 时扣 1.31 万，L40 时扣 3800，L80 时只扣 319。按原式会把建筑用料高估一到两个数量级，并得出“两万糖厂的熔炉用料占掉四分之一磁石储量”这种错误印象。

**修正：** 写成 U_r + Σ_j K_{r,j}·0.94^{L_j}（L_j 是开采那批料时的等级）。U_r 也要注明是“已扣掉的储量”，不是用掉的物品数。顺带的结论：建筑用的珍奇同样是越晚采越省。

### I2. “早期配额”的三个数字不能同时成立；而且早用在这个模型里是被支配的策略（一审 M3 的改法引入）

**原文（§4.3 三层答案 2）：**
> 以单极磁石为例：L6 时 0.22 个，L50 时 0.93 个，L81 时 4.2 个。因此磁石不必等到某一级才开始用，可以从一开始少量用起。

**问题：**
- 三个数都是用**开局全量** B=0.182M 算的，各自假设“从这一级起永远按这个量用”。它们是三个互斥的方案。读者很容易读成一条时间表（先 0.22，再 0.93，再 4.2），那样会超支。正确的滚动配额是 B_剩余(当时)/S(L)。
- 更要紧的是方向。每个白糖用一个磁石的收益（省建筑、省原油）与等级无关，而它的储量成本是 0.94^(n−1)，随等级单调下降。分级约束 Σ_n C(n)·0.94^(n−1)·a_r(x_n) ≤ B_r 是一个分数背包，收益/成本比随 n 递增，最优解是“某一级 L* 之前不用、之后放开用”的阈值策略。也就是说笑笑的“早用不如晚用”和 L80 阈值正是这个 LP 的最优结构，“从一开始少量用起”可行但不优。
- 报告把配额写成对笑笑结论的改进，没有做这一步分析。

**修正：** 第 2 条改写为：配额 B_剩余/S(L) 是“不会用完”的安全上限，不是建议用量；在本模型里最优策略是阈值型。只有当早期有别的硬约束（例如 S1 的原油、建筑数上限）被珍奇缓解时，早用才可能进入最优解，这要由带时间目标的多期模型判断。

### I3. 研究站增产被放进“存疑”，但它会把所有阈值整体前移；与笑笑的“独立复现”也因此只是同一简化下的一致

**原文（§4.1）：**
> 研究站增产（存疑）：如果研究站喷增产剂……S 也随之按比例变小。

**原文（§4.2 标题）：** “与笑笑的结论对照（独立复现）”

**问题：**
- 多个社区来源一致（Reddit “Proliferator effects overview”、Steam 讨论里 60→75 hash/s 的实测、dsp-wiki 用户页）：研究模式下喷过增产剂的矩阵按“额外产出”倍率多出哈希，Mk.III 为 ×1.25。若成立，每级白糖为 4000(n−5)/1.25，S 整体 ×0.8。
- 影响不小：笑笑档 3.28×0.8×S(L) ≤ 142k 的最小 L 从 81 变成 77；情形 A 从 98 变成约 94。终局玩家基本都会喷白糖。
- §4.2 的复现本身是对的：我核对了转写，556 879 = S(24)，3.28×556 879 = 1826.6k（笑笑说 1825k），“80 级”一行对应 S(81)。但它验证的是“算术和笑笑相同”，两边用的是同一个不含增产的模型。标题里的“独立复现”应降格。
- 另外 3.28 的容差极小：能得出 80 级的 a 的范围是 (3.118, 3.2805]，3.28×S(81)=141 978，离 142 000 只差 0.015%。这个系数来自 whisper 转写的“328”，小数点位置是推的。应写明。

**修正：** 把研究增产从“存疑”提到正文，给出两套 S（×1 与 ×0.8），并把它列为第一个要在游戏里核实的参数。§4.2 标题改为“与笑笑的算法一致”。

### I4. “终局最大白糖/分钟”始终没有算出任何数字

**原文（§0.3）：** “终局最大白糖/分钟是良定问题，但答案远超实际 CPU 能承受的规模。”

**问题：**
- 题目问的是“max white cubes”。报告列了约束，却没有对样例种子给出哪怕一个量级估计；“远超 CPU 能承受的规模”没有任何数字支撑。
- 手头的数据其实够做量级估计：
  - 光子：射线接收站 120 MW 出 6 光子/分，即 1200 MJ/光子。两万糖 × 0.8 光子 × 1200 MJ / 60 s = 320 GW，与笑笑的“光子请求 324 GW、2700 口锅”吻合（2700×120 MW = 324 GW）。所以每白糖/分约 16 MW 球功率，z_max ≈ 全星区戴森球功率 / 16 MW。
  - 原油：见 S1，采到下限后是 N_seep×0.1×(1+0.1L)/s。
  - 气巨：样例里每颗气巨的 `gases` × 8 × (1+0.1L) × 40 台就是上限。
- 结合 S1，本种子在 0.1 倍档下很可能是**原油**（而不是 CPU）先卡住，这与“远超 CPU”的说法相反。

**修正：** 增加一小节“样例种子的量级估计”，至少给出光子上限（按最亮几颗星满球）、原油上限、气巨上限三行。给不出戴森球功率就明说缺这个数，并删掉“远超”。

### I5. 生成器现在的输出不够支撑 §5.1 的模型

**原文（§5.1）：** “矿点数 Nodes_{k,p} 可以作为矿机布置的上限”“每个油泉的速率介于下限……与初始速率……之间”

**原文（§9.1）：** “新建 `GalaxyResources` 结构，包含星球、矿量、油泉、气巨、海洋、光度和巢穴数”

**问题：**
- DoubleUTH 的 `actualVeins` 只有每颗行星每种矿的**总量**（`{"veinType","amount"}`）。矿点数、每个油泉各自的储量、矿簇位置都只在 `planet.rs` 1053–1145 的循环内部，没有输出。
- 没有油泉个数就算不出原油下限（S1），没有矿点数就没有 Nodes。
- 黑雾设置：巢穴数由 `hive_initial_colonize`、`hive_max_density` 和种子共同决定（`star.rs` 482–520）。`seed_planets.py` 没有传这两个参数，用的是默认 1.0。样例里的 `hives=1/1` 不对应笑笑的“黑雾全拉满”存档。§2.1 的“由种子决定”应改为“由种子和黑雾设置决定”。

**修正：** §7、§9.1 写明要 fork DoubleUTH，除了加 `rlib`，还要把逐矿点（至少逐油泉）数据和黑雾设置暴露出来；工期相应上调。

### I6. 实施路线对“React + WASM 网页”这一形态考虑不足

- **原文（§7.1）：** “短期：子进程 + websocket，即本原型的做法。”网页不能起子进程。它只能连用户自己在本机启动的 `dsp_seed`（127.0.0.1:62879），这等于要求用户另外下载运行一个程序。对网页版，正路是把 DoubleUTH 编进 WASM（它本来就有 wasm-bindgen 目标，`tokio`/`rayon` 已按 target 隔离）。应把“中期”方案提为主方案。
- **原文（§6）：** “HiGHS 在 WASM 下是否可用还没评估（存疑）”。可以直接消掉：`lovasoa/highs-js`（MIT，2026-11-20 仍有推送）就是 HiGHS 的 WASM 构建。但要写明另一面：Rust 的 `highs` crate（rust-or/highs，Apache-2.0）绑定 C++，不能编到 `wasm32-unknown-unknown`。所以网页端要么从 JS 侧调 highs-js（模型以 LP 文本传过去），要么大模型只做本地 CLI。
- **多期 MILP（§5.2）在 microlp 上不现实。** microlp 0.8 的分支定界很基础，现有 `lp.rs` 靠时间上限兜底。科技解锁 big-M（M 取 `MAX_BUILDINGS`=10⁶ 量级时松弛极差）+ 等级 one-hot + 多星球，远超它的能力。建议路线里先做不含整数的版本：等级计划作为外生输入（报告已列为选项之一），科技解锁顺序固定，模型退化成 LP，microlp 就能解。
- **§9.2 “只需外层循环，不改求解器”只对 1 白糖/min 的连续 LP 成立。** 现在的做法是把 B_r/S(L) 塞进 `resource_limits`（变量上界）。目标产量不是 1、整建筑模式、或同时有别的产物时都会错。约束 raw_r·S(L) ≤ B_r·z 对 (raw, z) 是线性齐次的，应作为正式约束加进 `lp.rs`，并支持“目标产量为变量、求最大”，§5.3 的 max z 也需要它。可行性对 L 单调，外层用二分，约 8 次求解。

## 三、次要

- **m1 代码行号引用错位（一审 m6 的改法引入）。** §2.1：“稀有档会把大于 1 的系数取 ^0.8 再 ×0.7，母星再 ×2/3；32 ly 以外距离因子趋于饱和（`star.rs` 187–199 行）”。`star.rs` 187–199 只有距离因子（0.6·7^(d/32)，d>32 ly 时迭代对数）。^0.8、×0.7、×2/3 在 **`planet.rs` 651–660**。而且那是 `if 母星主题 { ×2/3 } else if 稀有档 { ^0.8, ×0.7 }`，二选一，不是“再”。
- **m2 油泉的距离加成是平方根。** `planet.rs` 705/1106：油用 `resource_coef^0.5`，气巨用 `^0.3`（525 行）。§2.1 只写了固体矿的规律，应补一句：远星的油和气增加得慢得多。
- **m3 “负熵熔炉每台 15 个单极磁石”。** `data/dsp.json` 里含 15 个磁石的是**位面熔炉**（plane-smelter：180/12）。负熵熔炉由位面熔炉升级而来，间接继承。改为“位面熔炉（及由它升级的负熵熔炉）”。
- **m4 §5.4 “可养殖基地数等于种子决定的太空巢穴数加上存档中的地面基地数”。** 太空巢穴和地面基地是两类对象，地面基地由巢穴派中继站落地建成，数量随时间变化，不是相加关系。笑笑养的是地面基地。改为：可养殖的地面基地数是存档状态，上限与该星系巢穴数和行星数有关，具体规则未核实。
- **m5 一次性掉落解锁规则漏了一条。** BWIKI 黑雾掉落页：已解锁设备但未解锁配方时只能拾取 40%。同页“3 分钟消失”原文带“（来源请求）”标记，应标存疑。
- **m6 “每个战场分析基站拾取 8 种物品 [BWIKI]”。** BWIKI 战场分析基站页只有一句“如需要多于8种材料，推荐多摆几个基站”，是间接说法；直接来源是笑笑（hints 第 91 行）。标注改为 [笑笑]，BWIKI 作旁证。
- **m7 a_r 不是常数。** 引力透镜（接收站每台 0.1/min）、翘曲器、防御弹药、黑雾防线补塔等消耗正比于**时间**而不是白糖数。研究第 n 级耗时 C(n)/z，所以这部分给判据加上一项 (c_r/z)·S(L)，z 越小越吃亏。另外规划器把 critical-photon 当原料，透镜消耗不在 a_r 里。应在 §4.1 的“修正与边界”里补一条。
- **m8 许可表述。** §2.4 “要保留 LICENSE 和 NOTICE”：仓库只有 `LICENSE.txt`，没有 NOTICE 文件。“ThemeProto 数据来自游戏资源，只能本地使用”没有依据，也和“可以 vendored 进本仓库”相矛盾：DoubleUTH 已经把这份数据随 Apache-2.0 仓库和 GitHub Pages 公开发布。改成“数据版权属游戏方，是否随本项目再分发需 Xinyu 决定”。
- **m9 最接近的先例没有读内容。** w1w218/dsp-seed-atlas 被称为“与本课题最接近的先例”，但报告只引了 README 一句“退火 + LNS”。它的规划器目标是“按目标配比（宇宙矩阵 / 戴森球）做基地选址与运输成本优化”，还有存档融合，正是 §5.1 和 §7.2 要做的事。至少应读 `src/docs` 的方案文档，说明它是否处理矿物利用和珍奇配额。README 还写明它的生成算法基于 baicai-1145/DspFindSeed，报告未提。另外 dsp-wiki 写明矿物利用最高 10 000 级，§3“消耗何时归零”一行可以补上。
